### 5.1 核心概念與技術原理

<!-- pdf-page 42 -->
#### 5.1.1 三種儲存架構
核心必考
| 比較項 | 資料倉儲 | 資料湖 | 湖倉一體 |
| --- | --- | --- | --- |
| 常見資料型態 | 結構化資料為主 | 原始資料與多種格式 | 同時處理多種格式與分析需求 |
| 典型資料管理 | 寫入前定義結構（Schema-on-Write） | 讀取時套用結構（Schema-on-Read） | 資料湖儲存搭配表格式與治理機制 |
| 主要用途 | BI 報表、固定分析 | 探索分析、模型訓練 | 結合 BI 與機器學習工作負載 |
| 主要風險 | 結構變更成本 | 治理不足會使資料難以搜尋或信任 | 架構與治理複雜度較高 |
Schema-on-Write vs. Schema-on-Read
Schema-on-Write：寫入時檢查既定結構，結構不符的資料可能被拒收。這可降低查詢時處理欄位型別的負擔，但**不保證內容在業務上正確或乾淨**；新增欄位或改結構也可能有成本。
Schema-on-Read：先原封不動存起來，讀取時才套用結構。優點是彈性極高、來得及保存原始樣
態；缺點是資料品質問題被延後到查詢端，且若無中繼資料管理就沒人知道裡面有什麼。

#### 5.1.2 OLTP與 OLAP
核心必考
| 比較項 | OLTP（線上交易處理） | OLAP（線上分析處理） |
| --- | --- | --- |
| 典型操作 | 高頻小量讀寫、單筆查詢 | 大範圍掃描與彙總 |
| 常見儲存方式 | 列式 | 欄式；也有其他實作 |
| 常見資料設計 | 正規化 | 星狀綱要（事實表＋維度表）等 |
| 主要要求 | 交易正確性與低延遲 | 查詢吞吐、壓縮率與彙總效率 |
為何分析型要用欄式儲存
分析查詢常是「掃描一億列但只用其中 3 個欄位」。欄式儲存可集中讀取所需欄位，通常減少不相關欄位的 I/O；同欄資料型態和值域相近，也常利於壓縮。實際效能仍取決於索引、壓縮、查詢及系統實作。
反之，OLTP常是「讀取或更新某一整筆訂單」，列式一次就能取得整列，效率較高。

> **易混字對照：列式／欄式**　本書維持臺灣用法（列＝row、欄＝column）。學習指引 4-14 的「**列式儲存**」就是本書的「**欄式儲存**」（columnar storage，如 Parquet／ORC）。兩者是同一件事；看到指引的「列式」請直接對應本書的「欄式」。

#### 5.1.3 NoSQL四型與 CAP
核心必考
| 類型 | 資料模型 | 典型用途 |
| --- | --- | --- |
| 鍵值 | key → value | 快取、工作階段狀態、計數器 |
| 文件 | JSON 類文件 | 內容管理、商品目錄、結構常變的資料 |
| 欄族 | 依欄族分組的稀疏表 | 大規模時序或日誌寫入 |
| 圖 | 節點與邊 | 詐欺關係網路、供應鏈追溯、推薦關聯 |
CAP 定理描述的是**發生網路分區時**的取捨：對分區兩側的請求，系統無法同時保證強一致性與每個請求都得到可用回應。「三選二」是記憶口訣，不能理解成平常運作時只能提供兩項性質。實務上須依資料與操作決定分區期間要拒絕部分請求以維持一致性，或容許暫時不一致以維持可用性。

#### 5.1.4 考點補丁：ACID 四性
核心必考

- **定義**：資料庫**交易（transaction）** 的四個保證。
  - **原子性（Atomicity）**：交易內的所有操作**全做或全不做**。轉帳時扣款與入帳不可只完成一半。
  - **一致性（Consistency）**：交易前後資料庫都滿足既定的完整性限制（如餘額不得為負、外鍵必須存在）。
  - **隔離性（Isolation）**：控制並行交易互相可見的程度；可避免哪些讀寫異常，取決於隔離等級。
  - **持久性（Durability）**：交易一旦提交，即使系統隨後斷電，結果仍然存在。
- **一句判斷規則**：題幹出現「扣款成功但入帳失敗，錢不見了」→ 原子性被破壞；出現「兩個併發交易看到對方的中間狀態」→ 隔離性問題；出現「斷電後已提交的資料消失」→ 持久性不足；出現「交易後違反已定義的資料庫約束」→ 一致性問題。
- **易混點**：
  - **一致性（Consistency）最常被誤解**。ACID 的 C 指的是「資料庫層級的完整性限制」，不是「業務邏輯正確」。業務層的檢查要靠應用程式或約束設計。
  - **隔離等級與效能需權衡**。較高隔離等級通常有額外成本，但實際併發效能依資料庫實作與工作負載而異。SQL 標準常列 Read Uncommitted → Read Committed → Repeatable Read → Serializable。
  - **ACID 不是關聯式資料庫獨有**。部分 NoSQL 系統也支援跨文件 ACID 交易；另一些系統在特定操作選擇最終一致性。應核對產品、版本與交易範圍，不可只憑「SQL／NoSQL」分類推斷保證。
- **隔離等級對應的異常**：

  | 隔離等級 | 髒讀 | 不可重複讀 | 幻讀 |
  |---|---|---|---|
  | Read Uncommitted | 可能 | 可能 | 可能 |
  | Read Committed | 不會 | 可能 | 可能 |
  | Repeatable Read | 不會 | 不會 | 可能 |
  | Serializable | 不會 | 不會 | 不會 |

  此表表示 SQL 標準的概念對照；實際資料庫對各隔離等級的行為可能不同，應查產品文件。

- **對應題號**：114-2 L22 Q07（正解 C）、114-2 L22 Q18（正解 A）。

#### 5.1.5 考點補丁：知識圖譜、RDF 三元組與圖資料庫
核心必考

- **定義**：
  - **知識圖譜（Knowledge Graph）**：以「實體—關係—實體」的網路表示知識，節點是實體，邊是關係。
  - **RDF 三元組（triple）**：知識圖譜的基本單位，格式為**主體（subject）—謂語（predicate）—受體（object）**，例如（台北 101，位於，臺北市）。
  - **圖資料庫（Graph Database）**：以節點與邊為第一級儲存單元的資料庫，查詢語言如 Cypher、SPARQL。
- **一句判斷規則**：題幹出現「多跳關係查詢」（朋友的朋友買過什麼）、「關聯本身就是資料」→ 圖資料庫；出現「以固定欄位記錄交易」→ 關聯式資料庫。
- **邊屬性（edge property）**：圖資料庫的邊**可以帶屬性**，例如（A，轉帳給，B）這條邊可帶「金額＝5000、時間＝2026-03-01」。這是圖資料庫與傳統關聯式「多對多中介表」的關鍵差異——中介表能記錄屬性，但多跳查詢要用多次 JOIN，隨跳數增加效能急遽下降。
- **易混點**：
  - **RDF 三元組是資料模型，不是資料庫**。三元組可以存在關聯式資料庫、三元組存儲（triplestore）或圖資料庫中。
  - **屬性圖（property graph）與 RDF 不同**：屬性圖的邊可帶鍵值對屬性，RDF 的邊就是一個謂語 URI，屬性是額外的三元組。
  - 知識圖譜的價值在**推論**：由（A 是 B 的子類）與（B 是 C 的子類）可推得（A 是 C 的子類）。
- **選型對照**：

  | 需求 | 首選 |
  |---|---|
  | 多跳關聯查詢、路徑分析 | 圖資料庫 |
  | 固定結構的交易紀錄 | 關聯式資料庫 |
  | 文件型、欄位常變動 | 文件型資料庫 |
  | 語意搜尋、相似度檢索 | 向量資料庫 |

- **對應題號**：114-2 L22 Q35（正解 B）、114-2 L22 Q34（正解 B）。

#### 5.1.6 考點補丁：資料庫選型
核心必考

- **四種主要類型的適用邊界**：

  | 類型 | 資料模型 | 強項 | 弱項 | 典型場景 |
  |---|---|---|---|---|
  | **關聯式（RDBMS）** | 表格＋固定 schema | **ACID 交易**、JOIN、約束 | 水平擴充難、schema 變更成本高 | 金融交易、訂單、帳務 |
  | **文件型（Document）** | JSON／BSON 文件 | schema 彈性、可按文件查詢 | 跨文件關聯與交易成本依產品實作而異 | 內容管理、商品目錄、日誌 |
  | **向量（Vector）** | 高維向量＋索引 | **相似度檢索**（ANN） | 不適合精確條件查詢與交易 | RAG 檢索、推薦、以圖搜圖 |
  | **圖（Graph）** | 節點＋邊 | 多跳關聯遍歷 | 大規模聚合分析弱 | 反詐欺、知識圖譜、社交網路 |

- **一句判斷規則**：題幹出現「需要跨多張表的一致性交易」→ 關聯式；「欄位常變、每筆結構不同」→ 文件型；「用自然語言找相似內容」→ 向量；「要找關聯路徑」→ 圖。
- **易混點**：
  - **向量資料庫不取代關聯式資料庫**。實務多是混合架構：關聯式存交易與中繼資料，向量庫存嵌入向量，兩者以 ID 對應。
  - **「NoSQL 一定比較快」是錯的**。效能取決於資料模型、索引、查詢型態與部署；不同 NoSQL 產品的交易與查詢能力也不同。
  - **ACID 與最終一致性是取捨不是優劣**。選型要看業務能否容忍短暫不一致。
- **組合選型的實務作法**：先確認「有沒有交易需求」→ 有則以關聯式為核心；再確認「主要查詢模式」→ 相似度檢索加向量庫、多跳關聯加圖庫、彈性文件加文件型。不要為了單一功能把整個系統換掉。
- **對應題號**：115-1 L22 Q13（正解 B）。

#### 5.1.7 考點補丁：分片、特徵商店與 Text-to-SQL
核心必考

- **分片（Sharding）**：
  - **定義**：依**分片鍵**（如使用者 ID 的雜湊值或日期範圍）把同一張表的**列**水平切開，分散到多個節點，每個節點只存一部分資料。
  - **一句判斷規則**：題幹出現「單一節點撐不住資料量或寫入量」→ 分片，目的是**水平擴展與負載分散**。
  - **易混點**：分片不是備份。多存幾份相同資料是**複寫（Replication）**，目的是可用性與讀取分流。分片鍵選得不好會產生熱點分片；跨分片的 JOIN 與交易成本也很高。
- **特徵商店（Feature Store）**：
  - **定義**：集中定義、計算、儲存與提供特徵的平台，同一個特徵（如「使用者近 30 天交易次數」）只開發一次，多個模型共用。
  - **一句判斷規則**：題幹出現「多個團隊重複計算相同特徵」→ 特徵商店，主要目的是**減少重複開發與維護成本**，並讓定義一致。
  - **附帶效益**：離線訓練與線上推論使用同一套特徵邏輯，可降低**訓練與服務偏差（training-serving skew）**；支援時間點正確的歷史特徵查詢（見第 11 章）。
- **Text-to-SQL**：
  - **定義**：由大型語言模型把自然語言問題轉成 SQL，交給資料庫引擎執行，再把結果回給使用者。
  - **一句判斷規則**：需求同時包含「非技術人員用自然語言提問」與「答案必須是精確的聚合統計」→ Text-to-SQL。計算由資料庫完成，因此結果精確，並沿用資料庫既有的權限控管與查詢稽核。
  - **易混點**：**RAG 適合從文件中找答案，不適合大規模數值聚合**。檢索回來的只是片段，語言模型自己「算」的數字不可靠。Text-to-SQL 的風險是產生錯誤 SQL，常見對策是提供資料表語意說明、使用唯讀帳號、執行前驗證 SQL，並把 SQL 顯示給使用者核對。
- **對應題號**：115-1 L22 Q14（正解 C）、115-1 L22 Q31（正解 B）、115-1 L22 Q36（正解 D）。


#### 5.1.8 供模型訓練的資料儲存
官方補充

- **訓練讀取的特性**：模型訓練是**大量、循序、重複**的讀取——每個 epoch 都要把整批資料再讀一次，瓶頸常在「資料餵給 GPU 的速度」。這和 OLTP 的「隨機、少量、頻繁更新」完全不同，所以不宜直接從線上交易庫讀訓練資料。
- **依資料型態選儲存格式**：

  | 資料 | 建議格式／位置 | 理由 |
  |---|---|---|
  | 表格特徵（欄位多、只用其中一部分） | Parquet、ORC 等**欄式**格式，放在資料湖或湖倉 | 只讀需要的欄位，壓縮率高（易混點：學習指引稱「列式儲存」，見 5.1.2） |
  | 大量小檔（影像、音訊） | 物件儲存保存原始檔；訓練時打包成數百 MB 的**分片檔**（如 TFRecord、tar 分片） | 避免數千萬個小檔的開檔與中繼資料開銷，可循序讀取 |
  | 嵌入向量 | 向量資料庫（檢索用）或陣列檔（訓練用） | 依用途分開：檢索看相似度搜尋，訓練看循序吞吐 |
  | 共用特徵 | 特徵商店的離線庫（訓練）與線上庫（推論） | 同一份特徵定義，避免訓練與服務偏差（見 5.1.7） |

- **開放表格式**：Delta Lake、Apache Iceberg、Apache Hudi 在物件儲存上的 Parquet 檔之外，加上**交易日誌**，提供 ACID 寫入、結構演進，以及**時間旅行**（讀取指定版本或時間點的快照）。訓練時記錄所讀的表格版本，就能重現當次訓練資料，也便於稽核。
- **分區與副本**：依日期等欄位**分區**，查詢只掃需要的分區（分區裁剪）；**副本**提供容錯與讀取分流，但不等於備份版本（見 5.1.7 分片與複寫）。
- **一致性**：訓練應讀**固定快照**。若邊寫入邊讀取，最終一致的儲存可能讓同一次訓練讀到新舊混雜的資料，結果無法重現。
- **一句判斷規則**：題幹出現「只用少數欄位」→ 欄式格式；「要重現某次訓練所用資料」→ 開放表格式的版本／時間旅行，或資料版本控制；「小檔太多、GPU 閒置等資料」→ 打包分片並平行預先載入。
- **易混點**：
  - 資料湖存原始資料不等於沒有治理；沒有版本與中繼資料，訓練資料無法追溯。
  - 物件儲存適合大量循序讀，不適合頻繁的逐筆更新。

#### 5.1.9 學習指引補充：強一致性與最終一致性
官方補充

- **強一致性**：寫入完成後，任何後續讀取都能讀到最新值；代價是寫入需要多個副本確認，延遲較高，網路分區時可能拒絕服務。
- **最終一致性**：寫入後各副本可能短暫不同，但在沒有新寫入的情況下，最終會一致；延遲低、可用性高，但可能讀到舊值。
- **一句判斷規則**：帳務、庫存扣減等不能讀到舊值的場景 → 強一致性；社群動態、商品瀏覽數等可容忍短暫落差的場景 → 最終一致性（見 5.1.3 CAP）。
- **易混點**：分區與副本、開放表格式（Delta Lake、Iceberg、Hudi）的內容見 5.1.8；副本提高可用性，但副本之間的同步方式才決定一致性等級。
- **指引頁碼**：學習指引科目二 4-11、4-13、4-15～4-17。

#### 5.1.10 學習指引補充：存取控制模型、零信任與資料目錄
官方補充

- **四種存取控制模型**：

  | 模型 | 授權依據 | 適用情境 |
  |---|---|---|
  | RBAC | 使用者所屬角色（工程師、分析師、主管） | 部門制組織、規則單純 |
  | ABAC | 使用者屬性、資料屬性與環境條件（地點、時間、裝置） | 需要細緻、動態授權 |
  | PBAC | 預先定義的複合策略規則 | 跨系統、雲端平台統一控管 |
  | DAC | 資料擁有者自行決定誰可存取 | 小型團隊、開發環境 |

- **零信任的三個原則**：**最小權限**（只給完成任務所需的最小資料範圍）、**即時授權**（Just-In-Time，權限依情境動態給予，避免長期累積）、**持續驗證**（多因子驗證與行為分析）；並以**微分段**把資源切成小區域分別防護。
- **資料目錄（Data Catalog）**：以元資料記錄資料的來源、格式、欄位定義、用途與授權狀態，支援資料血緣追蹤與跨部門欄位定義對齊。
- **一句判斷規則**：授權要依「時間、地點、裝置」動態判斷 → ABAC；「內部使用者也不預設信任」→ 零信任；「找不到資料在哪、欄位定義不一致」→ 資料目錄。
- **指引頁碼**：學習指引科目二 4-18、4-19。

### 5.2 常見陷阱與錯誤觀念
• 以為資料湖不需要治理。沒有中繼資料、存取控制與生命週期管理，資料湖會迅速變成資料沼
澤。
• 把 OLAP需求塞進 OLTP資料庫。在正式交易庫上跑大範圍彙總查詢，會拖垮線上服務。
• 以為 CAP可以三者兼得。在網路分區發生時，只能在一致性與可用性之間擇一。
• 以為 NoSQL一定比 SQL快。NoSQL是以放寬某些保證換取特定場景的效能，並非全面較
優；需要跨表交易一致性時關聯式資料庫仍是正解。
• 忽略欄式儲存不適合頻繁單列更新。欄式適合讀多寫少的分析場景。

#### 模擬題 SIM-L22202-001

模擬題 SIM-L22202-001 ｜ 選型題 ｜ 難度：中級 ｜ 對應 L22202
某電信商需分析三年份、每日數十億筆的通話明細，典型查詢為「依區域與月份彙總通話時長」，僅
使用 50個欄位中的 4個。下列儲存設計何者最為適當？
(A)使用列式儲存的 OLTP關聯式資料庫，並建立大量索引
(B)採用欄式儲存的分析型資料庫，並以星狀綱要組織事實表與維度表
(C)全部存入鍵值資料庫，以通話 ID為 key
(D)存成大量小型 CSV檔案，查詢時再逐一讀取
答案與逐項解析
答案：B
(A) ×列式儲存必須讀取整列才能取得那 4個欄位，在數十億筆規模下 I/O成本極高；且 OLTP資
料庫的設計目標是交易一致性而非大範圍掃描。
(B)✓正解。查詢型態是「大範圍掃描、少數欄位、彙總」，正是欄式儲存的最佳場景——只讀取需
要的欄位、壓縮率高。星狀綱要則讓維度篩選（區域、月份）高效。
(C) ×鍵值資料庫擅長依 key單筆取值，無法有效支援跨區域與時間範圍的彙總查詢。
(D) ×大量小檔案會造成嚴重的中繼資料負擔與 I/O效率低落（小檔案問題），且無壓縮與述詞下推
能力。
干擾項設計理由：(A)利用「建索引就會快」的直覺，忽略了掃描型查詢與點查詢的本質差異。
延伸考點：欄式格式（如 Parquet類）的兩項關鍵優勢為欄位裁剪與述詞下推，可在讀取階段就跳
過不需要的資料塊。此與 Chapter 6 的 Spark查詢優化直接相關。

#### 模擬題 SIM-L22202-002

模擬題 SIM-L22202-002 ｜ 觀念題 ｜ 難度：中級 ｜ 對應 L22202
關於 CAP定理之敘述，下列何者最為正確？
(A)分散式系統可以同時完全滿足一致性、可用性與分區容忍性
(B)由於網路分區無法避免，實務上是在保有分區容忍性的前提下，於一致性與可用性之間取捨
(C) CAP定理只適用於關聯式資料庫
(D)選擇可用性即代表系統永遠不會回傳錯誤資料
答案與逐項解析
答案：B
(A) × CAP 定理指出：網路分區發生時，系統無法同時保證一致性與可用性，必須取捨其一。
(B)✓正解。在真實網路中無法排除分區發生，因此 P不是選項而是前提；真正的設計決策是分區發生
時要「拒絕服務以保一致」（CP）還是「先回應可能過時的資料」（AP）。
(C) × CAP是分散式系統的通則，與資料模型無關。
(D) ×恰好相反——選擇可用性意味著在分區期間可能回傳尚未同步的舊資料。
干擾項設計理由：(D)把「可用」誤解為「正確」，是本主題最常見的混淆。
延伸考點：金融轉帳偏 CP（寧可交易失敗也不能餘額不一致）；社群動態、商品瀏覽偏 AP（看到
晚幾秒的資料無妨，但服務不能中斷）。命題常以業務情境要求判斷該偏哪一端。

#### 模擬題 SIM-L22202-003

模擬題 SIM-L22202-003 ｜ 選型題 ｜ 難度：中級 ｜ 對應 L22202
某銀行欲建置系統，分析帳戶之間的轉帳網絡以找出可能的人頭帳戶集團，典型查詢為「找出與某

(A)鍵值資料庫
(B)欄族資料庫
(C)圖資料庫
(D)文件資料庫
答案與逐項解析
答案：C
(A) ×鍵值只支援依 key取值，無法表達與遍歷關係。
(B) ×欄族擅長大量寫入與依列鍵查詢，不擅長多層關聯遍歷。

(D) ×文件資料庫適合結構常變的獨立文件，跨文件關聯查詢並非其強項。
延伸考點：圖分析在金融犯罪防制的典型應用包括社群偵測（找出緊密相連的帳戶群）與中心性分析
（找出集團中的關鍵節點）。此議題於 Chapter 8有進一步處理。

#### 模擬題 SIM-L22202-004

模擬題 SIM-L22202-004 ｜ 程式判讀 ｜ 難度：基礎 ｜ 對應 L22202
關於下列讀檔程式之敘述，何者錯誤？

```python
df= pd.read_csv('log.csv', usecols=['ts','region','duration'], dtype={'region':'category'})
print(df.dtypes)
print(df.memory_usage(deep=True).sum())
```

(A)usecols只讀取指定欄位，可顯著降低記憶體用量
(B)將region指定為 category型別，在重複值多時可大幅節省記憶體
(C)df.dtypes回傳 Series，列出各欄型別
(D)ts欄會被自動解析為日期時間型別，無須額外指定
答案與逐項解析
答案：D
(A)✓正確，這是欄位裁剪概念在單機讀檔上的體現。
(B)✓正確。category以整數編碼加對照表儲存，重複值多時記憶體大幅下降。
(C)✓正確。
(D) ×錯誤（即為答案）。read_csv不會自動把字串欄解析為日期時間，預設會讀成 object字串。須
明確指定parse_dates=['ts']，否則後續的時間運算與排序都會以字串處理而產生錯誤結果。
干擾項設計理由：(D)利用「欄名叫 ts應該會被認出來」的期待，這是實務上極常見的疏漏。
延伸考點：字串型日期的排序是字典序，在格式為YYYY‑MM‑DD時碰巧與時間序一致，但格式若為M/
D/YYYY就會完全錯亂。這也是資料品質六構面中「有效性」的檢核重點。


#### 模擬題 SIM-L22202-005

模擬題 SIM-L22202-005 ｜ 情境題 ｜ 難度：中級 ｜ 對應 L22202
某平台每天新增數億筆點擊紀錄，保存在物件儲存。模型訓練只用到 300 個欄位中的 12 個，而且稽核要求能重現三個月前某次訓練所用的資料。下列方案何者最適當？
(A)每天存成一個 CSV 檔，訓練時全部載入記憶體再挑選欄位
(B)以 Parquet 存放並用開放表格式（如 Delta Lake 或 Iceberg）管理，依日期分區，每次訓練記錄所讀取的表格版本
(C)全部寫入線上交易用的關聯式資料庫，以主鍵逐筆查詢讀取
(D)以 JSON 存放，每週覆寫成最新版本以節省空間
答案與逐項解析
答案：B
(A) × CSV 是逐列文字格式，只要 12 欄也得讀完全部內容；且沒有版本機制，無法重現歷史資料。
(B)✓正解。欄式格式只讀需要的欄位；分區讓查詢只掃相關日期；開放表格式的版本紀錄（時間旅行）可重建當次訓練資料。
(C) × 交易庫為隨機小量讀寫設計，大量掃描會拖垮線上服務，逐筆讀取也極慢。
(D) × 覆寫會讓舊版本消失，直接違反可重現的稽核要求。
干擾項設計理由：(D)用「節省空間」吸引考生，卻犧牲了題幹明確要求的可重現性。
延伸考點：若不用開放表格式，也可用資料版本控制工具或不可變的日期快照目錄達成相同目的；重點是「每次訓練都有可追溯的資料版本」。

#### 模擬題 SIM-L22202-006

模擬題 SIM-L22202-006 ｜ 診斷題 ｜ 難度：中級 ｜ 對應 L22202
某團隊以四張 GPU 訓練影像分類模型，訓練資料是存在物件儲存中的 3,000 萬張 JPEG 小檔（平均 50 KB）。監控顯示 GPU 使用率長期低於 30%，而資料讀取的 I/O 等待時間很高。下列改善何者最直接有效？
(A)把影像轉存到關聯式資料庫的二進位欄位
(B)把影像打包成數百 MB 的分片檔循序讀取，並以多個工作行程預先載入下一批資料
(C)把影像轉成 CSV 文字格式
(D)再增加四張 GPU
答案與逐項解析
答案：B
(A) ×資料庫的二進位欄位不適合大量循序讀取，瓶頸只是換個地方。
(B)✓正解。問題出在數千萬個小檔的開檔與中繼資料開銷；打包成大分片可循序讀取，平行預先載入則讓 GPU 不必等資料。
(C) ×文字格式體積更大、解碼更慢。
(D) ×瓶頸在資料供應端，增加 GPU 只會讓更多 GPU 閒置。
延伸考點：判斷訓練瓶頸先看 GPU 使用率與 I/O 等待；GPU 閒置而 I/O 高，就是資料管線問題，不是算力問題。
