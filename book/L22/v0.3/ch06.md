#### 6.1.1 批次與串流
核心必考
| 比較 | 批次處理 | 串流處理 |
| --- | --- | --- |
| 處理單位 | 有界資料集（例如一天、一個月） | 持續到來的事件流 |
| 延遲 | 常為分鐘至小時 | 可達毫秒至秒，依系統設計而定 |
| 典型引擎 | 分散式批次運算框架 | 事件串流平台搭配串流運算引擎 |
| 適用 | 月結報表、大規模模型訓練、歷史回溯 | 即時風控、物聯網告警、動態定價 |
| 關鍵指標 | 吞吐量、完成時間 | 端到端延遲、背壓處理 |
選型訊號
「每日凌晨統一計算」「重跑歷史三年資料」→批次。
「交易發生當下就要判定」「感測器持續送出讀值」→串流。
微批次（micro-batch）是折衷：把串流切成很短的批次處理，延遲通常在秒級，兼顧吞吐與實作簡
易度。

#### 6.1.2 Hadoop與 Spark的關鍵差異
核心必考
Hadoop MapReduce的 map 輸出寫到本機磁碟，作業之間經 HDFS 落地；兩者都要磁碟往返，而機器學習與圖演算法需要反覆
掃描同一份資料，每次迭代都付出一次磁碟往返成本，因此極慢。
Spark以記憶體中的分散式資料集進行運算，中間結果可保留在記憶體，迭代式任務可快上一至兩個
數量級。
| 元件 | 角色 | 備註 |
|---|---|---|
| HDFS | 分散式檔案系統，分塊與多副本儲存 | 提供容錯與高吞吐循序讀取 |
| YARN | 叢集資源管理 | 分配容器與記憶體等資源 |
| MapReduce | 批次運算模型 | 跨階段運算常經磁碟與儲存系統交換資料 |
| Spark | 通用分散式運算引擎 | 可讀取 HDFS；在許多工作負載中可作為 MapReduce 的替代運算層 |
常見陷阱與錯誤觀念
常見誤述：「Spark取代了 Hadoop」。正確理解是 Spark取代的是 MapReduce這個運算層，仍
常搭配 HDFS或物件儲存作為儲存層、YARN或其他排程器作為資源層。

#### 6.1.3 Spark的三個必考特性
核心必考

<!-- pdf-page 51 -->
##### 6.1.3.1 一、惰性求值與 DAG
filter、select、map、withColumn、join等轉換（Transformation）不會立即執行，只建立執行計畫（有
向無環圖）；直到遇到行動（Action）才真正計算。
此設計讓查詢優化器能重排、合併與下推運算——例如把filter推到讀取階段，直接少讀資料。
##### 6.1.3.2 二、Transformation與 Action的分辨

| Transformation（不執行） | Action（觸發執行） | 易混淆者 |
| --- | --- | --- |
| select、filter、where | count() | df.count()是 Action，回傳整數；df.groupBy(...).count()是 Transformation，回傳 DataFrame |
| groupBy、agg、join | show()、take()、collect() | 兩者名稱都有 count，作用完全不同 |
| orderBy、distinct | write、foreach | write本身即為 Action |
本章第一名考點
df.count()→Action，立刻運算並回傳一個整數。
df.groupBy("region").count()→Transformation，回傳一個新的 DataFrame，什麼都還沒算。
這組對比在程式判讀題中出現頻率極高。

<!-- pdf-page 51 -->
##### 6.1.3.3 三、Shuffle與資料傾斜
Shuffle指跨節點的資料重分配。觸發者包括groupBy、join、distinct、repartition、orderBy。它牽涉
磁碟寫入與網路傳輸，是分散式作業中最昂貴的操作。
資料傾斜（Data Skew）指某一個 key的資料量遠大於其他，導致單一 task拖垮全局——其他 99個
task都完成了，就等那一個。
| 優化手段 | 作法 | 常見適用情境 |
|---|---|---|
| 減少 Shuffle | 先過濾、減少需重分配的資料量，並檢查分割方式 | 大量跨節點交換資料時 |
| 廣播 Join | 將小表送至各執行節點，避免對大表全面重分配 | 大表連結足夠小的維度表 |
| 加鹽（Salting） | 拆散極端熱門的 key，再彙總結果 | 單一 key 高度集中 |
| 預先分桶 | 依 Join key 分桶儲存，並配合引擎可利用的條件 | 反覆以相同 key 連結；是否省 Shuffle 須看執行計畫 |

#### 6.1.4 Kafka與事件串流
核心必考
Kafka是分散式事件串流平台，以主題（Topic）與分區（Partition）組織訊息，提供高吞吐、持久化
與重放能力。
在資料架構中的三個核心價值：
1.解耦生產者（物聯網裝置、應用系統）與消費者（特徵計算、模型推論、資料湖寫入）——雙方不需
彼此知道存在。
2.緩衝——下游故障或流量尖峰時，訊息仍保留在 Kafka中不遺失。
3.重放——新的消費者可從頭讀取歷史訊息，便於補算或新增下游應用。
分區決定並行度與順序保證：Kafka只保證同一分區內的訊息順序，跨分區無全域順序。若某類事件
必須依序處理（如同一帳戶的交易），應以該帳戶 ID作為分區鍵。

#### 6.1.5 時間語意與視窗
核心必考
串流處理必須區分：
• 事件時間（Event Time）：事件實際發生的時間（裝置產生讀值的時刻）。
• 處理時間（Processing Time）：系統收到的時間。
網路延遲與離線緩衝會使事件亂序到達。正確的統計必須依事件時間，並設定水位線（Watermark）
容許一定程度的遲到資料——水位線越寬容，結果越正確但延遲越高。
| 視窗型態 | 定義 | 典型用途 |
|---|---|---|
| 滾動視窗 | 固定長度且不重疊 | 每 5 分鐘的交易總額 |
| 滑動視窗 | 固定長度，按指定步長移動；可重疊 | 每分鐘更新「過去 5 分鐘」的移動平均 |
| 會話視窗 | 依事件間隔切分，長度不固定 | 使用者一次瀏覽工作階段 |
產業延伸（非官方核心考點）
特定產品之組態參數（如分區數調校、消費者群組再平衡策略、串流引擎的檢查點設定、各家雲端
託管服務比較）屬產業延伸。官方此代碼備註欄空白；不宜將本章工具清單視為官方逐項要求，也不需記憶產品參數。

#### 6.1.6 考點補丁：近似分位數（串流摘要）
核心必考

- **定義**：在**單次掃描、記憶體有限**的串流資料上估計分位數（如中位數、P95、P99）的演算法。代表方法為 **t-digest** 與 **KLL sketch**；**Count-Min Sketch** 則是估計**頻率**的類似技術。
- **為什麼不能精確算**：精確分位數必須保存全部數值（或排序後的完整清單）。串流場景資料量無上限，記憶體有上限，因此必須以**近似**換取**有界的記憶體與單次掃描**。
- **一句判斷規則**：題幹出現「資料持續流入、無法全部存下」「只要即時監控 P95／P99 延遲」「記憶體有上限」→ 近似分位數（sketch）；出現「資料已落地、可以排序」→ 精確算法即可。
- **誤差保證**：這類演算法的價值在於提供**可證明的誤差上界**（例如 ε-approximate），而不是「猜一個大概」。考題若問「如何確保近似結果可用」，答案是**指定誤差參數並驗證上界**，不是「加大記憶體」。
- **易混點**：
  - **平均值可以串流精確計算**（只需維護和與計數）；**分位數不行**。這是兩者最關鍵的差別。
  - 近似分位數**不保證單一查詢的精確值**，但保證排名誤差在界內。
  - **合併性（mergeability）** 是實務重點：多個 sketch 可合併成一個，才能做分散式聚合。
  - **標準差、變異數也可以分散式精確計算**：各分區只要回傳筆數 n、總和 Σx、平方和 Σx²（或等價的局部統計量），彙總後即可得到全體變異數。Spark 直接用 `df.agg(F.stddev("col"))` 或 `RDD.aggregate()`；絕不可 `collect()` 把十億筆資料拉回 driver 再算。
- **常見方法對照**：

  | 方法 | 估計什麼 | 特點 |
  |---|---|---|
  | t-digest | 分位數 | 對尾部（P99）精度較好 |
  | KLL sketch | 分位數 | 誤差有嚴格理論界 |
  | Count-Min Sketch | 頻率 | 只會高估，不會低估 |
  | HyperLogLog | 基數（不重複計數） | 極省記憶體 |

#### 6.1.7 考點補丁：服務水準協議（SLA）
核心必考

- **定義**：**SLA（Service Level Agreement，服務水準協議）** 是服務提供者與使用者之間對**服務品質**的正式約定，載明量測指標、目標值、量測方式與未達標的後果。
- **三個必分清的名詞**：

  | 名詞 | 意思 | 有無賠償後果 |
  |---|---|---|
  | **SLA** | 對外的正式協議 | 有（通常為補償或罰款） |
  | **SLO** | 對內的服務水準目標 | 無直接賠償，是內部管理線 |
  | **SLI** | 實際量測到的指標 | 無（它是量測值） |

- **常見 SLI 與目標寫法**：可用性（99.9%）、回應時間（P95 < 200 ms）、錯誤率（< 0.1%）、吞吐量（每秒請求數）。
- **一句判斷規則**：題幹出現「合約載明未達標要補償」→ SLA；出現「團隊內部設定 99.9% 目標」→ SLO；出現「實際監測到的成功率」→ SLI。
- **易混點**：
  - **可用性百分比要換算成停機時間才有感覺**：99.9% ≈ 每年 8.76 小時；99.99% ≈ 每年 52.6 分鐘；99.999% ≈ 每年 5.26 分鐘。考題常要求換算。
  - **SLA 是平均值或分位數的約定，不是每次請求的保證**。「P95 < 200 ms」允許 5% 的請求超過。
  - **AI 系統的 SLA 要納入模型指標**。除了系統可用性，還須約定模型準確率下限、漂移監控頻率與重訓承諾；只約系統可用性會出現「服務正常但模型早已失準」的靜默失效。
- **與 AI 導入評估的連結**：SLA 是 L21201 成本效益分析的一部分——可用性等級每提高一個 9，成本通常呈倍數成長。規劃時要先問「業務真的需要幾個 9」，而不是直接追求最高等級。
- **對應題號**：115-1 L22 Q29（正解 D，題幹）。

#### 6.1.8 考點補丁：物聯網資料管線
核心必考

- **定義**：大量感測器同時產生資料時，常見架構分三層：**邊緣運算節點**（靠近設備，先做過濾與即時判斷）→ **串流處理框架**（持續計算視窗統計、觸發告警）→ **雲端資料湖**（完整保存原始資料，供後續訓練與分析）。
- **一句判斷規則**：題目同時要求「毫秒級反應」與「完整資料留存供訓練」→ 選**邊緣＋串流＋資料湖**。只有批次處理、報表系統或人工處理的選項，都無法滿足即時性。
- **各元件分工**：

  | 元件 | 解決什麼 |
  |---|---|
  | 邊緣運算 | 省去往返雲端的網路延遲，就地判斷異常 |
  | MQTT | 輕量的發布／訂閱通訊協定，負責**傳輸**，不負責計算與儲存 |
  | Kafka 等事件平台 | 緩衝、解耦與重放（見 6.1.4） |
  | 串流處理框架 | 對事件流做連續計算與告警 |
  | 資料湖 | 以原始格式保存全量資料 |
  | 資料倉儲 | 保存整理過的結構化資料，供報表使用 |

- **易混點**：
  - 資料倉儲是 Schema-on-Write，會丟掉不合格式的原始細節；要保留完整原始資料給 AI 訓練，應放**資料湖**。
  - 「即時儀表板」只是呈現層，本身不做即時運算。
  - 用 REST API 逐筆輪詢，在上萬台設備的規模下，延遲與負載都難以接受。
- **對應題號**：114-2 L22 Q11（正解 C）、114-2 L22 Q19（正解 C）。

### 6.2 程式判讀重點
核心必考
惰性求值：哪一行才真正運算

```python
df2= df.filter(df.status=="OK")#Transformation：不執行
df3= df2.groupBy("region").count()#Transformation：不執行
df3.write.parquet("/out/result")#Action：此時才真正計算
```

判讀重點：前兩行執行後不會有任何資料被讀取，即使df有一兆列也是瞬間完成。第三行觸發整條
DAG，且groupBy會產生 Shuffle。
count的兩種身分

```python
n= df.count()#Action->int
g= df.groupBy("city").count()#Transformation->DataFrame
g.show()#Action->此時才運算
```

collect的記憶體風險與正確除錯方式

```python
rows= df.collect()#危險：把「全部」資料拉回 driver，大表直接記憶體溢出
```

#### 6.2.1 考點補丁：pandas 資料處理必考語法
核心必考

- **定義**：公告試題的程式題集中在六類操作：型別、缺失值、讀大檔、篩選、分組排序、合併。每一類都有一個「看起來對、其實錯」的干擾寫法。
- **一句判斷規則**：先問「這行回傳什麼」，再問「分母或範圍對不對」。例如「總貢獻最高」要先加總再排序，「只保留有對應資料的紀錄」是 inner join。
- **型別與缺失值**：

  | 現象或需求 | 正確理解或寫法 | 干擾寫法 |
  |---|---|---|
  | 整數欄被讀成 `float64` | 欄中有 NaN（NaN 是浮點數），或原檔本來就寫成 `2019.0` | 「pandas 預設把所有數值讀成 float」 |
  | 含 NaN 的欄轉整數 | `astype("Int64")`（大寫 I，可容納缺失值的整數型別） | `astype(int)` 會拋錯；`fillna(0)` 會捏造年份 0 |
  | 計算各欄缺失數 | `df.isna().sum()` 或 `df.isnull().sum()`（兩者同義） | `df.isnan()`、`df.isNaN()` 不是 DataFrame 方法 |
  | 右偏欄位少量缺失 | 以**中位數**填補（`fillna(df[c].median())`） | 平均數會被長尾拉高；最大值更偏 |

- **讀大檔**：`pd.read_csv(path, chunksize=100_000)` 回傳可逐批迭代的讀取器，每批處理完再處理下一批，是「記憶體放不下整個檔案」的正解。`dtype` 可以降低記憶體，但檔案遠大於記憶體時不夠；`nrows` 只讀前 N 筆，會遺漏資料；`usecols` 接受欄名清單，不接受比例。
- **篩選、分組、合併**：

  ```python
  orders[orders["region"] == "North"]["amount"].mean()   # 布林遮罩篩選後取平均
  orders.groupby("user_id")["amount"].sum().nlargest(3)  # 先加總再取前三
  scores.nlargest(5, "score")                            # 依某欄取前五筆
  pd.merge(orders, users, on="user_id", how="inner")     # 只保留兩邊都有的鍵
  ```

- **易混點**：
  - `groupby(...).max()` 取的是單筆最大，不是總貢獻；`sort_values(...).head(3)` 排的是單筆交易，同一客戶可能重複出現。
  - `how="left"` 保留左表全部列（右表沒有的補 NaN）；`how="outer"` 兩邊全部保留；`pd.concat(axis=1)` 依**索引**並排，不依鍵對齊。
  - `orders["region" == "North"]` 先在 Python 算出 `False`，不是篩選。

#### 6.2.2 考點補丁：scikit-learn 與 statsmodels 的建模 API
核心必考

- **定義**：scikit-learn 的估計器都遵循同一組介面：`fit` 學習參數，`transform` 套用轉換，`predict` 產生預測。statsmodels 則以統計報表為主，引數順序與 scikit-learn 不同。
- **一句判斷規則**：scikit-learn 一律 **X 在前、y 在後**；statsmodels 的 `OLS` 是 **y 在前、X 在後**，而且不會自動加截距。
- **標準流程**：

  ```python
  from sklearn.model_selection import train_test_split
  from sklearn.preprocessing import StandardScaler
  from sklearn.linear_model import LogisticRegression

  X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2, random_state=0)
  scaler = StandardScaler()
  X_tr_s = scaler.fit_transform(X_tr)   # 只在訓練集學平均與標準差
  X_te_s = scaler.transform(X_te)       # 測試集沿用訓練集的參數
  clf = LogisticRegression().fit(X_tr_s, y_tr)
  ```

- **statsmodels 對照**：

  ```python
  import statsmodels.api as sm
  Xc = sm.add_constant(X)          # 手動加入截距欄
  ols = sm.OLS(y, Xc).fit()        # y 在前
  print(ols.summary())             # 係數、標準誤、p 值
  ```

- **易混點**：
  - `train_test_split` 回傳順序固定為 `X_train, X_test, y_train, y_test`，接錯順序會把特徵當標籤。
  - `scaler.fit(X)` 回傳的是 scaler 物件本身，不是轉換後的資料；要拿到資料須呼叫 `fit_transform` 或 `transform`。
  - `LinearRegression` 的 `coef_` **不含截距**，截距在 `intercept_`。
  - 判斷各係數是否顯著要看 statsmodels 報表中**每個係數的 p 值**，不能因整體 F 檢定顯著就說所有係數都顯著。
- **對應題號**：114-2 L22 Q50（正解 B，程式圖）、115-1 L22 Q48（正解 C）、115-1 L22 Q49（正解 B）。

### 6.3 常見陷阱與錯誤觀念
• 以為filter執行後資料就被過濾了。惰性求值下什麼都還沒發生。
• 對大表呼叫collect()。driver記憶體溢出的頭號原因。
• 說「Spark取代 Hadoop」。取代的是 MapReduce運算層。
• 忽略 Shuffle成本。在join前先過濾與投影，可大幅減少搬移的資料量。
• 以處理時間做視窗統計。事件亂序時結果會錯，且無法重現。
• 以為 Kafka保證全域順序。只保證同一分區內有序。
• 把資料傾斜當成叢集資源不足。加機器無效，須從 key分布著手。

#### 模擬題 SIM-L22203-001

模擬題 SIM-L22203-001 ｜ 程式判讀 ｜ 難度：中級 ｜ 對應 L22203
執行下列 PySpark程式後，關於其行為之敘述何者正確？

```python
df2= df.filter(df.status=="OK")
df3= df2.groupBy("region").count()
df3.write.parquet("/out/result")
```

(A)第一行執行時即完成全表掃描並產生中間結果集
(B)前兩行僅建構執行計畫，不觸發運算；第三行寫出時才執行。未預先依 region 相容分割的資料
在 groupBy 聚合時通常需要 Shuffle
(C)groupBy屬於 Action，故第二行即觸發完整運算
(D)三行皆為 Transformation，須另行呼叫collect()才會執行
答案與逐項解析
答案：B
(A) ×filter為 Transformation，採惰性求值，不會立即掃描。
(B)✓正解。filter與groupBy皆為 Transformation，Spark僅記錄血緣關係建構 DAG；write為
Action，此時優化器才產生實體執行計畫並實際運算。同一 region 的資料需要匯聚；若輸入未
依該鍵相容分割，通常須經 Shuffle，可能成為效能瓶頸。實際是否有 Exchange 應以執行計畫確認。
(C) × groupBy回傳 GroupedData，接 count()後仍是 DataFrame轉換，不是 Action。務必區分
df.count()（Action，回傳整數）與df.groupBy(...).count()（Transformation，回傳 DataFrame）。
(D) ×write本身即為 Action；對大表呼叫collect()會把資料集中到 driver，可能耗盡記憶體。
延伸考點：常見 Action：count()、collect()、show()、take()、write、foreach。groupBy、join、
distinct、repartition、orderBy 等操作通常涉及 Shuffle；是否發生仍取決於資料分割與執行計畫。

#### 模擬題 SIM-L22203-002

模擬題 SIM-L22203-002 ｜ 診斷題 ｜ 難度：整合 ｜ 對應 L22203
某 Spark作業共 200個 task，其中 199個在 3分鐘內完成，剩下 1個執行超過 40分鐘。經查該
作業以customer_id進行groupBy，而某一個匿名帳戶 ID佔全部資料的 35%。下列處置何者最為適
當？
(A)增加叢集節點數量，讓運算資源更充裕
(B)此為資料傾斜；應對傾斜 key加鹽分散後分兩段聚合再合併，或把該 key單獨抽出處理後再
與其餘結果聯集
(C)將groupBy改為orderBy即可避免
(D)對該 DataFrame呼叫collect()後在 driver端單機處理
答案與逐項解析
答案：B
(A) ×資料傾斜的瓶頸是單一 task，加機器不會讓那一個 task變快，其他節點只會閒置。這是最常
見的錯誤處置。
(B)✓正解。典型資料傾斜。加鹽是在傾斜 key後附加隨機後綴，把一個超大分組拆成多個小分組
先各自聚合，最後再合併結果。
(C) ×orderBy同樣觸發 Shuffle，且無助於分散單一 key的資料量，反而可能更慢。
(D) ×把大量資料拉回 driver 會增加記憶體不足的風險，且失去分散式運算的效益。
干擾項設計理由：(A)是直覺反應——「慢就加機器」，但完全無效，屬本題最具鑑別力的誘答。
延伸考點：實務上「匿名帳戶」「未知」「其他」這類預設值最容易造成傾斜。除加鹽外，也可先將該
key單獨抽出處理再與其餘結果聯集。診斷方法是查看各 key的資料筆數分布。

#### 模擬題 SIM-L22203-005

模擬題 SIM-L22203-005 ｜ 程式判讀 ｜ 難度：中級 ｜ 對應 L22203
下列程式意圖檢視資料，但在 5億列的 DataFrame上執行後導致程式崩潰。原因與修正為何？

```python
rows= df.collect()
print(rows[:10])
```

(A)collect()語法錯誤，應改為collect(10)
(B) collect()會把全部資料拉回 driver節點，5億列造成記憶體溢出；應改用 df.show(10)或
df.limit(10).collect()
(C)應增加 executor記憶體即可解決，程式寫法無誤
(D)因為collect()是 Transformation，須再加一個 Action才會執行
答案與逐項解析
答案：B
(A) ×collect()不接受筆數參數；限制筆數應用take(n)或先limit(n)。

片[:10]發生在資料已全部拉回之後，完全來不及避免溢出。
(C) ×崩潰的是 driver而非 executor；且即使加大 driver記憶體，把 5億列放進單機仍不可行。
(D) ×collect()是 Action，不是 Transformation。
干擾項設計理由：(C)針對「記憶體不足就加記憶體」的直覺，忽略了問題出在架構層面的取用方
式。
延伸考點：除錯時的正確取樣方式：df.show(n)（直接印出，不回傳）、df.take(n)（回傳前 n列的清
單）、df.limit(n).toPandas()（轉為本機表格）。三者都先在叢集端限制筆數。

模擬題 SIM-L22203-006 ｜ 觀念題 ｜ 難度：中級 ｜ 對應 L22203

(A)以處理時間分視窗，因為系統收到的時間最準確
(B)以事件時間分視窗，並設定適當的水位線容許遲到資料，再輸出該視窗結果

#### 模擬題 SIM-L22203-007

模擬題 SIM-L22203-007 ｜ 觀念題 ｜ 難度：中級 ｜ 對應 L22203
某公司以 Kafka承接各系統事件。工程師發現同一帳戶的兩筆交易被下游以錯誤順序處理。最可能
的原因與修正為何？
(A) Kafka不保證任何順序，此問題無法解決
(B) Kafka僅保證同一分區內的順序；該帳戶的訊息被分散到不同分區，應以帳戶 ID作為分區鍵使
其進入同一分區
(C)應減少消費者數量至 1，才能保證順序
(D)應改用批次處理，因串流本質上無法保證順序
答案與逐項解析
答案：B
(A) × Kafka提供分區內的順序保證，並非完全無序。
(B)✓正解。Kafka的順序保證範圍是分區。若未指定分區鍵，訊息由預設分區器分配，同一帳戶的訊息不保證落在同一分區，同一
帳戶的訊息因而可能被不同消費者以不同速度處理。以帳戶 ID為分區鍵可確保同一帳戶的所有
訊息落在同一分區，依序處理。
(C) ×把消費者減為 1雖能緩解，但會犧牲全部並行度與吞吐量，是以效能換正確性的下策；且若
訊息本就分散在多分區，單一消費者跨分區讀取仍無全域順序保證。
(D) ×順序問題與批次或串流無關，而是分區設計問題。
延伸考點：分區鍵的選擇是順序保證與負載平衡的權衡——以帳戶 ID分區可保證順序，但若某大戶
交易量極高，會造成分區間的資料傾斜，與 Spark的傾斜問題同源。
